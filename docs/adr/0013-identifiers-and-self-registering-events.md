# 0013. Identifiers and self-registering events

- Status: Accepted
- Date: 2026-11-02

## Context

`circle.create` and `member.join` are signed by a device the server has never seen, so the usual "look up the device's key" check cannot work. The spec also leaves open how ids are chosen.

## Decision

- `CircleId`, `MemberId` and `DeviceId` are random 128-bit values, lowercase hex (32 characters), generated by the client. `EventId` is 64 lowercase hex characters.
- `circle.create`, `member.join` and `device.add` carry a device registration in `public`: `member`, `device`, `signPub`, `boxPub` (32-byte keys). For `circle.create` and `member.join` the registered device must be the envelope's own `author` and `device`, and the signature is checked against `signPub` from the same event (self-certifying). For `device.add` the signature is checked against the existing device's stored key; the new device's member must be the author, or the author must be a steward.
- `member.join` also carries `invite` (id of the `member.invite` event) and `proof`: an Ed25519 signature by the invite key over `"circles/join/v1"` followed by the circle, member and device ids (as their hex text) and the signing and box public keys (raw bytes). The server checks the invite exists in that circle, is not expired (`day <= expiresDay`) and has uses left.
- A device id or member id that is already registered is rejected, so nobody can re-register someone else's id after the fact.

## Consequences

Device ids are not bound to keys, so someone could register an id first and block the real owner (squatting). With random 128-bit ids that is not guessable; the risk is accepted for v1 (ids are only known once published in the log). Revisit with a derived id if it matters. The server stores the founder as the first steward from `circle.create`.
